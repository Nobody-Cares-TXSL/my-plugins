# Git 规范提交并推送

按约定式提交规范准备 Git 提交，并在用户确认后提交、推送。用户只要求提交时，完成提交即可。

## 输入与工具

- Claude Code CLI：从 `$ARGUMENTS` 或用户消息读取提交信息，使用 Bash 执行 Git；使用 AskUserQuestion 确认。
- Codex：从用户消息读取提交信息，使用当前可用的命令执行工具。确认使用支持审批的工具或直接在对话中询问；不要将仅供偏好选择的工具用于权限请求。没有回复就等待，不将默认选项或超时视为同意。
- 安装、加载、修改本技能不代表用户要求执行提交或推送。

## 提交信息

格式：`<type>(<可选 scope>): <description>`，按需追加 body 和 footer。

- type 使用 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`、`ci` 或 `build`。
- description 不超过 50 字符；body 说明做了什么、为什么；用户已提供的信息尽量保留。
- 只引用已知的 issue，按需使用 `Closes #123`、`Fixes #123` 或 `BREAKING CHANGE:`。

## 执行流程

1. **分析变更**：读取 `git status --short`、`git diff`、`git diff --cached`，核对当前分支及 upstream。未跟踪文件要先读取内容。只处理本次请求相关文件。
2. **准备提交**：展示拟定提交信息、文件清单及相关验证结果。已有暂存内容属于其他任务时，先确认提交范围，不自动取消暂存或混入提交。
3. **确认提交**：取得用户对本次提交内容的明确确认后再暂存、提交。用户在当前会话已确认相同内容时沿用授权；文件范围或提交内容变化后重新确认。
4. **精确暂存**：使用具体文件路径，如 `git add -- src/main.py`；禁止 `git add .` 或 `git add -A`。检查暂存 diff，确保实际提交范围与确认内容一致。
5. **创建提交**：标题和正文作为正确引用的独立 `-m` 参数传递，或用文件工具写入消息文件后 `git commit -F <绝对路径>`。消息文件放在环境提供的临时目录。保留真实换行，不把提交文本拼成可执行 shell 代码，不依赖 `cat`、HEREDOC 或命令替换。
6. **确认推送**：用户要求推送时，展示提交 hash、标题、目标 remote 和分支，单独取得推送确认。只确认提交不代表确认推送；取消推送时保留本地提交。
7. **推送并核对**：按确认的目标执行推送，核对命令结果和分支状态。没有 upstream 或目标不明确时先询问，不猜测 `origin/main` 等目标。

## 失败与边界

- Git 命令失败立即停止，报告错误和可行下一步；不绕过 hooks、不使用 `--no-verify`、不自动重复提交或推送。
- 提交失败先确认是否已经生成提交，修复原因后再决定是否新建提交；不得自动 amend，除非用户明确要求。
- 不执行交互式 Git 操作。未经明确授权，不执行 force push、reset 或修改历史。
- 任务完成后报告提交 hash、标题和推送状态；仅准备方案时不要声称已经提交。
