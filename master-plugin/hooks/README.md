# hooks — Claude Code Mods

这里维护 `master-plugin` 中 Claude Code Mod 的入口、模块职责、运行边界和验证方法。本文以当前实现为准；Mod API 的通用规则见 [Claude Code Mods 速查](../../DOC/cc_mods.md)。

## 1. 目录与加载关系

```text
hooks/
├── hooks.json          # Claude Code Mod 入口声明
├── register.js         # 统一注册入口
├── prompts.js          # 本地 Prompt Library
├── html-link.js        # HTML 文件路径链接
├── prompt-optimize.js  # 输入框草稿优化
└── README.md           # 本文
```

`hooks.json` 的 `modules` 指向 `register.js`。该入口再 import 各模块，并依次调用它们的 `register(on, options)`：

1. `prompts`
2. `html-link`
3. `prompt-optimize`

新增或移除 Mod 时，修改 `register.js`，并同步更新本文的模块索引、事件和测试说明；通常不需要修改 `hooks.json`。

## 2. 模块索引

| 模块 | 注册事件 | 运行范围 | 职责 |
|---|---|---|---|
| `prompts.js` | `session.start`、`command.run{command=prompts}`、`ui.render{component=Pane}` | Terminal、Desktop 显示面板；其他 surface 返回文本 | 搜索、浏览本地 Markdown 提示词并填入输入框 |
| `html-link.js` | `ui.render{component=AssistantMessage}` | 仅 Terminal 全屏消息视图 | 将存在的本地 HTML 文件路径显示为可点击链接 |
| `prompt-optimize.js` | `ui.render{component=AbovePrompt}`、`prompt.edit`、`prompt.change` | Terminal、Desktop | 按推理档位重构当前草稿，只回填、不发送 |

这里的运行范围是各模块当前代码中的实际判断，不代表所有 Claude Code surface 都支持相同的界面能力。

## 3. prompts：本地提示词库

使用 `/prompts [关键词]` 打开 Prompt Library。它读取本地 Markdown 文件，在面板中浏览、搜索和选择提示词，再将内容填入当前输入框。

### 配置与扫描

- **目录配置**：读取插件清单 `userConfig.promptsDirectory`，默认 `~/.claude/prompts`；支持 `~/` 开头的路径或绝对路径。
- **扫描范围**：递归扫描目录及普通子目录中的 `.md` 文件。
- **跳过内容**：符号链接、空文件，以及任意层级中名称为 `CLAUDE.md`、`AGENTS.md`、`README.md` 的文件（文件名不区分大小写）。
- **显示名称**：使用文件中第一个一级标题（`# 标题`）；没有标题时使用文件名。
- **目录导航**：没有搜索词时，只显示当前目录的提示词和直接子目录；进入子目录后可以返回上一级。
- **全文搜索**：有搜索词时，跨所有已扫描目录匹配名称、相对路径和文件全文，不需要先进入对应目录。

### 预览与填入

面板选择提示词后，会显示文件开头的 YAML Frontmatter 元数据；这不是正文预览。可执行以下操作：

| 操作 | 行为 |
|---|---|
| 插入光标处 | 将提示词全文插入输入框当前光标位置 |
| 追加到末尾 | 将提示词全文追加到输入框末尾 |
| 替换输入内容 | 用提示词全文替换当前输入 |
| 插入文件路径 | 将该提示词文件的绝对路径插入光标位置 |

填入后面板保持打开，可以继续选择其他提示词。刷新按钮会重新扫描目录；重新执行 `/prompts` 也会重新加载。

### 运行边界与成本

- Terminal 和 Desktop 支持面板。
- 其他 surface（例如 `claude -p`、VS Code 聊天面板）不绘制面板，而是返回提示词列表文本。
- 每次打开或刷新都会递归读取符合条件的 Markdown 文件全文，再在内存中搜索；当前没有文件系统监听，也没有增量索引。
- 文件内容、搜索词、当前目录和选择状态保存在模块级变量中。模块重载会重置这些状态；不会将提示词内容写入插件自己的持久化存储。

**使用建议**：将配置目录指向专用 Prompt 文件夹。不要直接把包含大量文档的整个知识库当作提示词目录，否则每次打开或刷新都可能产生较多文件读取和内存占用。

## 4. prompt-optimize：三档任务意图重构

在 Terminal 或 Desktop 的输入框上方提供三个按钮：`low优化草稿`、`medium优化草稿`、`high优化草稿`。用户选择档位后，模块读取当前草稿，调用当前会话模型重构任务，再将结果替换输入框内容。

**它只修改草稿，不会提交提示词。按 Enter 仍由 Claude Code 正常发送。**

### 模型调用

| 档位 | effort | 请求超时上限 |
|---|---|---:|
| low | `low` | 8.5 秒 |
| medium | `medium` | 14 秒 |
| high | `high` | 22 秒 |

- 使用 `await $.session.model()` 获取当前会话模型，不强制切换模型。
- 每次点击只调用一次 `$.model.complete()`，不自动重试，也不自动切换模型。
- 三档均设置 `maxTokens: 850`。超时是请求上限，不是实际耗时保证。
- 模型只收到当前草稿和模块的系统指令，不会自动获得当前对话历史或项目文件上下文。

### 比较、回填与还原

- 如果输入框仍是上一次优化结果，切换档位时会重新使用最初草稿作为输入，避免在上一版改写上继续改写。
- 优化成功后，只回填改写结果，不把原文附加到结果末尾。
- 「还原上次优化」仅在输入框仍保持该次优化结果时恢复原稿。
- 用户在优化期间修改草稿时，模块会检测到内容变化并放弃回填，避免覆盖新内容。
- 用户手动编辑已优化的草稿后，还原快照会失效，不会用旧原稿覆盖新编辑。

### 输入与输出校验

- 输入草稿长度限制为 6～6000 个字符。
- 模型可以返回 `IMPROVE_SKIP`，表示原文已足够清晰或不值得重写。
- 改写结果必须使用约定的 `REWRITE` 输出格式，正文长度为 12～2200 个字符。
- 程序会检查输出格式，并检查原稿中的 URL、`@` 引用、特定形式的路径（如 `~/`、`/home/`、`./`、`../`）和数字字面量是否保留；不满足时拒绝回填。
- 这些程序检查**不等于语义验证**。否定条件、授权边界、业务含义是否被准确保留，主要依赖模型指令，仍需要用户检查优化结果。

### 失败与数据边界

模型取消、超时、空响应、格式异常、硬约束遗漏、权限错误、限流或网络问题都会给出状态提示；失败时保留当前草稿。模块不会因为优化成功而自动发送内容。

草稿会作为模型请求内容发送给当前会话模型。不要把「不自动发送」理解为「内容不会离开本机」；处理敏感信息前应先检查草稿内容及当前模型的数据处理边界。

## 5. html-link：本地 HTML 路径链接

在符合运行条件的助手消息下方追加一行链接，例如：

```text
⎿  report.html ↗
```

点击链接时重新检查文件是否存在，然后尝试使用系统浏览器打开本地文件。

### 识别与展示

- **识别内容**：裸写的本地路径、行内代码中的路径、Markdown 链接目标，以及裸写的 `file://` 绝对路径。
- **忽略内容**：代码围栏中的路径、`http://` / `https://` 等普通网络 URL，以及 `.xhtml`。
- **中文相邻文本**：ASCII 开头的 token（例如 `23-张截图.html`）优先作为完整路径；中文开头的 token（例如 `见index.html`）会先尝试从中文与 ASCII 的边界处分割，再尝试完整 token。像 `见中文文件.html` 这种正文和文件名都可能成立的情况，无法仅凭纯文本可靠区分。
- **相对路径**：按该消息第一次进入处理时记录的 cwd 解析，避免用户之后执行 `cd` 导致旧消息指向改变。
- **存在性**：只有 `$.fs.stat()` 确认目标是文件时才展示链接。
- **数量**：每条消息最多展示 20 个候选文件。
- **追加方式**：先调用 `await next(e)` 获取后续渲染结果，再追加自己的链接行；不替换原消息正文。
- **点击时复查**：点击时再次 stat。文件已被删除或不再是文件时，通过 toast 提示，不会继续打开。

### 缓存与去重边界

- `cwdOf` 按 `requestId` 保存消息首次绘制时的 cwd，采用最多 **512 条**的 LRU 缓存。命中时不重复读取 cwd；超出容量时淘汰最久未使用的消息记录。极旧消息若在记录被淘汰后再次重绘，会按当时的 cwd 重新解析相对路径。
- `statCache` 按绝对路径缓存文件状态，采用最多 **1024 条**的 LRU 缓存。确认存在的文件缓存 **30 秒**；不存在或 stat 失败的路径缓存 **1 秒**，避免流式重绘反复触发文件系统查询。
- `session.end` 会清空两类缓存，覆盖会话结束以及 `/clear`、`/resume`、`/branch` 等会话切换；模块重载也会自然重置缓存。
- 文件在正向缓存有效期内被删除时，消息中的链接可能暂时仍显示；点击时会重新 stat，确认文件不存在后提示用户。文件新建后，负向缓存最多延迟 1 秒才会重新检查。
- 按**绝对路径**去重。同一文件的不同锚点只保留一个链接；不同目录下的同名文件分别保留。只有发生同名冲突时，才把链接标签从 basename 扩展为相对 cwd 的路径；cwd 之外的文件显示绝对路径。

### 打开方式

- **Linux**：优先读取 `xdg-settings get default-web-browser`，解析默认网页浏览器的 desktop 文件 `Exec=`，并直接向浏览器传入本地 `file://` URL。无法解析时回退到 `xdg-open`，再尝试 `open`。
- **Windows**：使用 `cmd /c start` 打开文件。
- **参数安全**：通过参数数组启动进程，不拼接 shell 命令；每次尝试的超时为 5 秒。
- **反馈**：打开成功或失败都会显示 toast。

### 与 mdview 的依赖

`html-link` 必须位于 `mdview` 的外层，也就是插件加载顺序中 **master-plugin 应先于 mdview**。

原因：本模块需要先执行自己的 hook，再通过 `await next(e)` 获取内层渲染结果并追加链接。如果 `mdview` 位于外层，并在处理含 `.md` 的消息时直接替换整棵树且不调用 `next`，本模块就没有机会执行。

不要在文档中固定记录插件的序号；`enabledPlugins` 的实际顺序可能变化。应检查当前启用配置，确保 master-plugin 排在 mdview 前面。

**手动验收**：让助手在同一条回复中同时输出一个存在的 `.md` 路径和一个存在的 `.html` 路径，确认 mdview 的 Markdown 展示正常，且下方仍出现 HTML 链接。单独含 HTML 路径的消息不足以覆盖这个顺序冲突场景。

## 6. 测试与验证

从仓库根目录 `/home/duan/plugins` 执行：

```bash
# 运行插件内自动化测试
claude plugin test ./master-plugin

# 检查插件清单、Mod 注册事件和 API 调用
claude plugin validate ./master-plugin

# 使用本地工作副本启动 Claude Code，便于实际交互验收
claude --plugin-dir ./master-plugin
```

### 当前自动化测试覆盖

目前有两个自动化测试文件，共 **18 项测试**：

- `tests/prompt-optimize.test.ts`（15 项）：三档按钮、当前会话模型、effort 与超时配置、跨档位比较、手动还原、输出约束、编辑冲突保护、取消与失败状态，以及不自动发送。
- `tests/html-link.test.ts`（3 项）：同名不同路径分别展示、同一文件的重复锚点去重、重复渲染复用缓存、`session.end` 清理缓存，以及超过 1024 条时淘汰最久未使用的文件状态记录。

**prompts 目前没有对应的自动化测试文件。** html-link 的自动化测试也不覆盖真实浏览器启动、点击后的桌面行为或与 mdview 的跨插件顺序；这些仍需手动验收。`claude plugin validate` 通过不代表这些界面和集成行为已经验证。

### 手动验收清单

- **prompts**：检查目录扫描、跳过规则、嵌套导航、跨目录全文搜索、四种填入操作、刷新和非 Terminal/Desktop 的文本降级。
- **prompt-optimize**：检查三个档位、跨档位比较、还原、编辑冲突保护、失败保留原稿，以及 Enter 不触发优化。
- **html-link**：检查裸路径、行内代码、Markdown 链接目标、代码围栏排除、文件不存在、点击打开，以及与 mdview 的混合消息场景。

## 7. 维护约定

新增或调整 Mod 时，同步检查以下内容：

1. `register.js` 是否正确 import 并调用模块。
2. 本文的模块索引、事件、surface 和行为说明是否与代码一致。
3. 是否引入新的模块间或跨插件执行顺序依赖。
4. 是否需要增加自动化测试；无法自动化的部分应列入手动验收清单。
5. 对缓存、权限、模型调用和文件系统行为的描述，是否准确反映实际实现，而不是把设计意图写成程序保证。

本文记录当前实现及其已知限制。若文档与代码冲突，应先核实代码和运行行为，再同步修正文档；不要仅为让测试或文档通过而改变既定行为。
