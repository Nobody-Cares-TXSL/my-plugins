# 最终实施计划

这是给主对话的计划撰写要求。在原生 Plan Mode 中完成必要的探索、方案推演、关键文件复核和需求澄清后，准备撰写最终计划时读取。使用已获得的 `Explore` 和 `Plan` 结果作为参考，以实际代码和用户约束为准。产出是可实施、可验证的架构与执行步骤；完整代码留到实现阶段。

## 1. 任务目标与影响范围

- 写清要改变的行为、成功条件和必须保留的现有行为。把明确不做的事留在范围之外。
- 根据实际执行链说明涉及的入口、模块或层次及各自职责；用 `file:line` 或符号引用标出关键改动位置。涉及共享逻辑时，列出需要同步的调用方、导出、配置、测试和 fixtures，避免只覆盖入口。
- 修复 Bug 时，区分已经核实的触发条件、根因和仍待复现的假设，说明为何选定该位置修复。

## 2. 按依赖顺序列实施步骤

每一步说明四件事：**改哪里、改什么、依赖什么、怎么确认完成**。先写下游依赖的接口或共享行为，再写调用方迁移与验证；必要时标明哪些步骤可以并行。优先复用已有实现和项目约定，只在会影响此次取舍时比较备选方案。

涉及跨层契约时，写明必要的函数签名、字段、输入输出、错误行为和边界条件。接口说明以能交给实现者为止，不给出完整函数、补丁或大段伪代码。

## 3. 验收与待确认项

- 将关键步骤对应到可执行的测试、检查命令或手动场景，写明预期结果和回归范围。命令应来自当前仓库；没有确认命令时标明待核验。
- 对权限、数据损失、外部行为或关键接口的未决事项，在对应步骤旁标记 **待确认**，说明它会阻塞什么。能通过读代码或运行无副作用的检查确认的事项，先确认再写计划。
- 最后核对：实现者能否按顺序完成，审查者能否据此查 diff 和验证各项结果。纯规划任务到此交付；后续是否实现沿用原生审批及用户授权。
